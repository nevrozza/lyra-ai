# Model selection and context

## Select and run the model

1. Honor the model the user named. When the choice is delegated, call `inspect` for the shortlist and inspect one or two promising exact tags. Use `model_intelligence.low`, `.medium`, and `.high` from inspect. Low is only for trivial, fully specified mechanical fixes (typos, literal replacements, formatting); never delegate implementation or fixes requiring reasoning to Low. Medium is the minimum for writing code, debugging and refactoring. High is preferred for complex implementation, architectural or subtle behavioral fixes and review. Escalate after a failed attempt; never downgrade merely to save memory. Unclassified models require evidence of sufficient capability. For final review, choose the strongest eligible model suited to the whole change among those that did not write it. Keep model tags out of reusable instructions and examples.
2. For Pi, `benchmark_and_settings.pi_check: true` means the model passed Lyra's check. Prefer it when available. Lyra rejects `false` and `ollama_agent_tools: unsupported`. For an untested model (`pi_check: null`), prefer `ollama_agent_tools: advertised` over `unknown`. Read `inspect.auto_context.solo_tokens` and `parallel_tokens` with `solo_source`, `parallel_source`, `solo_reason` and `parallel_reason`. Prefer compatible measured context points in `benchmark_and_settings.memory_profile` for memory and per-window timing decisions. Use `profile_gpu_bytes` only for verified cold points; reported Ollama RAM/VRAM can disagree with device-wide sampled usage. An unavailable recommendation is not permission to invent a small or large window. For a model without usable data, ask the user to run the full dashboard benchmark or deliberately use an explicit supported context based on available evidence. Normally omit `context_tokens`: a saved manual setting wins, otherwise Lyra sizes the window at dispatch. Use `parallel: false` for a lone worker; set `parallel: true` only when independent tasks benefit from concurrency and their shared window is sufficient. Explicit overrides remain available for user requests or deliberate recovery. Compare with `max_context_tokens` when reported. Missing estimates are unknown, not evidence that a large context fits. Treat the estimated context as a resource constraint, not a measure of reasoning ability or task complexity. Compare available benchmark timings, prior task results, expected rework and shared GPU contention when choosing model, scope and parallelism.
3. Among suitable models, consider warm residency or startup time for short jobs and measured generation speed for longer jobs. Use `manage_model` for useful preloading or to manage idle models within the user's residency requirements. Respect pinned models and active work. Use `set_description` only for a requested catalog-description edit. For text-only work use a saved project chat in Chat mode; honor the user's residency preferences when selecting the model.
4. Give `run_pi` a self-contained prompt with both saved project/chat IDs. An explicit context on `run_pi` or a queued step applies to that run or step and uses an Ollama profile for that size. Auto is not persisted as a manual choice. Lyra budgets estimated weights, FP16 cache and compute overhead; it reserves space for parallel requests and distinct runners, reuses compatible active profiles, and does not count pinned or active memory as reclaimable. Estimates are conservative and hardware-dependent. Pi reports an actionable Auto error when no safe window is known; load/pin may retain the provider default with a diagnostic. The measured profile is only valid for its recorded hardware, model and visible settings; it does not establish the cost of every workload. A new automatic runner may wait for existing work to release memory. Do not poll to watch it.

Use the saved Thinking preference when present. Leave the model's default otherwise, especially for review, correctness checks, and Thinking tests. Saved Chat and Work runs and queued tasks use the saved Thinking setting or Ollama's default. Keep Thinking directives out of prompt text. Lyra no longer imposes or accepts a configurable output-token cap for `run_pi` or queued tasks. Do not pass `max_output_tokens`. Context windows and model/provider limitations still apply. Normal Pi execution no longer has a fixed 15-minute timeout; startup, benchmark and command timeouts remain.

## Interpret the result

- `context_notice: near_limit` in a running queue call or `context.notice: near_limit` in a result means the next turn benefits from a compact prompt or fresh history. `compacting` and `compacted` describe history compaction. Continue to check the task result.
- `stop_reason: context_full` or a queued status of `context_full` calls for context recovery. Read `context.context_tokens` from `run_pi.structuredContent` or the queued `result`. The reported value is Pi's context window.
- `stop_reason: length` can indicate the output limit. Check `truncated`, any error and `work_progress.diagnostics` before accepting the result. Compare the last input + output usage with the configured window, observed Ollama context and provider hook limit. The hook payload is not a network capture; an unexplained length stop is not proof of a specific finite cap. Workers report their own outcome through finish_task within the original run. Lyra does not send automatic completion or continuation prompts even when the confirmation is missing. A Work task with a provider-reported `length` stop pauses in `output_limit` (or `context_full` if context exhaustion is identified). Inspect the actual saved evidence and decide whether the remaining assignment needs a smaller slice or a different context window. Do not assume `stop` proves the worker finished the assignment.
- Treat cancelled, interrupted, or otherwise failed work as incomplete. Inspect saved results and work already done before deciding whether to retry.

## Recover an overflow

Budget for inputs and outputs from every tool call when deciding how much work to assign one chat. Compaction adds a model call and can drop details the next worker would need. Prefer a fresh chat for a separable step when a compact verified handoff costs less than preserving useful history; pass only relevant files, constraints and results. Use the recovery paths below when proactive splitting could not avoid pressure.

| Situation | Direct Pi chat | Queued task |
| --- | --- | --- |
| Useful history and memory for a larger window | Call `inspect` with the exact model and candidate context. Call `run_pi` on the same project and chat with a larger `context_tokens` and a compact continuation. Keep passing that size on subsequent turns that need it. | Call `retry_project_task` with the original task ID, a strictly larger `context_tokens`, and a compact continuation. |
| Mostly stale history or a tight memory budget | Call `create_project_session` with the same registered working folders and primary folder first. Then call `run_pi` with the new chat ID and the handoff. | Call `retry_project_task` with the original task ID, `fresh_chat: true`, and the handoff. Omit `context_tokens` to reuse the previous window, or supply a different size when appropriate. |
| Fresh, compact run still overflows | Reduce the files, prompt, or task slice. Report a blocker when there is no useful change to make before another retry. | Narrow the remaining work within the existing write scope, or report the blocked step and its waiting dependents. Avoid replaying the same request unchanged. |

For output exhaustion rather than a full context window, read the structured `work_progress` (`result.work_progress` for queued work) and compact saved tool results via `read_project_session`. Successful guarded mutations prove that operations happened, not that the requirements passed; missing or pending results are not confirmation. Use `retry_project_task` on `output_limit` with a compact continuation, normally reusing the same chat and window, or `fresh_chat: true` when history no longer helps. Do not replay confirmed writes; inspect current files, then finish remaining work or just the missing verification/handoff. Dependents stay waiting until the original task succeeds. A user-cancelled task is never eligible for this recovery.

A useful handoff carries the goal, scope, constraints, the relevant files and changes already made, remaining work, and the acceptance check. Preserve the old transcript. Ask Pi to inspect the current files before repeating edits, since an overflow can happen after a successful write. Use `read_project_session` to recover the few missing facts you need.

After a queued retry, call `await_project_tasks` on the original `project_session_id` (no polling). Use the returned `chat_session_id` with `read_project_session` to inspect the new transcript. The queue preserves the original model, role, file scope, dependencies, and automatic follow-up.
